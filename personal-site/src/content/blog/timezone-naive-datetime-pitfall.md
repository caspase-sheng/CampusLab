DDL 页面自测时发现，新建一条截止时间设成「今晚 23:59」，列表里却显示成第二天 07:59，整整偏了 8 小时。数据没丢、也没报错，是时区语义在三层之间没对齐。

## 三层是怎么错位的

后端一开始是用 `datetime.now(timezone.utc)` 生成时间的，带时区的那套写法。往 SQLite 里存的时候，SQLite 的 DATETIME 列不保留时区偏移，只把 UTC 的钟面值（年月日时分秒）原样存下来。读回来就是一个 naive 的 datetime，比如 `2026-10-20 15:59:00`，虽然它本身表示的是 UTC 的 15:59。

前端拿到这个不带时区的字符串 `"2026-10-20T15:59:00"`，`new Date(...)` 一进去，按 JS 的规范，这种不带时区的串会被当成**本地时间**解析，也就是把它读成了本地 15:59。本地 15:59 换成实际时刻，比用户选的本地 23:59 早了 8 小时。

三步单独看好像都「没错」：后端老实存 UTC，数据库老实存钟面值，前端按规范解析本地时间。错在它们对同一个字符串的含义理解不一致——同一个 `15:59`，在一层眼里是 UTC，在另一层眼里是本地。

## 定位过程

先在浏览器里把响应原样复制出来，看串里到底有没有 `Z` 或 `+08:00`：

```js
console.log(item.due_time);         // "2026-10-20T15:59:00"，没有时区标记
console.log(new Date(item.due_time).getHours()); // 15，被当成本地时间了
```

再翻后端，确认 `created_at` / `due_time` 这些字段当时确实用了 `datetime.now(timezone.utc)`，而契约里的 DateTime 类型根本没开 `timezone=True`，SQLite 也就不可能帮我们留住偏移。两头一对，结论很清楚：不是精度问题，是「这个串属于哪个时区」没定死。

## 修法：全项目统一成本地 naive

一开始想在前端补个 `+8`，或者把串手动改成带 `Z` 的。但那样只治了一个字段，别的接口早晚还会漏。落下来的做法是反过来，把后端的时间统一成本地 naive：

- 模型上的 `DateTime` 一律不带 `timezone=True`，默认值从 `datetime.now(timezone.utc)` 改成 `datetime.now()`；
- 前端存进去和显示出来都按本地时间处理，因为后端存的本来就是本地钟面值，前后端对得上，不再整段平移；
- DDL 的截止时间本来就是用户在 `datetime-local` 输入框里按本地时间选的，统一成本地 naive 之后，选 23:59 存的就是 23:59，读出来还是 23:59。

前端那个 `formatDateTime` 里也是按本地时间取字段（`getFullYear` / `getHours` 这一组），和「后端存本地 naive」这条约定配套。

选本地 naive 而不是一路用 UTC，主要是因为这个项目里 `due_time` 天然是「用户眼里的本地时间」。如果一部分字段存 UTC、一部分存本地，两种语义混在一张表里更难收拾。全都用本地 naive，至少规则是统一的。

## 记几点

- 时间字段的坑不一定是精度（秒 / 毫秒），更常见的是语义：这个值到底表示哪个时刻、属于哪个时区。
- 前后端对时间的理解得在一处定死。约定写进模型默认值和前端格式化工具里，比散落在各个接口里靠谱。
- SQLite 不认时区，`timezone=True` 这种写法在它这里基本等于没写，别指望数据库帮你保留偏移。
