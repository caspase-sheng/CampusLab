CampusLab 是一个完全本地运行的全栈校园学习平台。日常功能是课程表、DDL 和笔记三块增删改查；另外塞了一套自己写的 Bitcask 风格 KV 存储引擎，和两个把算法中间状态回放成动画的可视化页面。KV 引擎现在是独立子系统，还没有和业务数据打通。

## 技术栈

- 后端：FastAPI + SQLAlchemy + SQLite
- 存储：自研 Bitcask 风格 KV 引擎（段文件追加写 + 内存索引 + LRU 读缓存）
- 前端：React 19 + Vite + Tailwind 4
- 可视化：排序（冒泡 / 插入 / 归并 / 快速）与图搜索（BFS / DFS / Dijkstra），算法在前端算好整段帧再回放

## 核心功能

- 课程表：按星期排课，前端手搭一张 08:00–22:00 的周视图
- DDL 管理：填截止时间、可关联课程、可一键切换 pending / done
- 笔记：普通的 SQLite 增删改查，标题 / 正文 / 逗号分隔标签
- KV 存储引擎：set / get / del / keys / stats / compact，带 TTL 和崩溃恢复
- 算法可视化：把排序和图遍历的中间状态拍成帧序列回放，排序可视化可以在这里点着玩：[实验室 →](/lab)
- 统一响应信封与错误码：后端 `/api` 下所有接口返回 `{ code, message, data }`

## 实现要点

### KV 引擎：段文件追加写 + KeyDir 索引 + LRU 读缓存

这个引擎照 Bitcask 那套思路写，代码在 `backend/app/kv/` 下。写操作先往磁盘段文件末尾追加一条记录，再更新内存里的 KeyDir 索引，返回成功；同一个键改多次，段文件里就有多条记录，读的时候认最后那条。记录头是固定 21 字节（crc32 + 操作码 + key 长度 + value 长度 + 8 字节过期时间戳），crc32 从操作码一直校验到 value 末尾。内存里只留两份东西：KeyDir 记 `key -> (段号, value 偏移, 长度, 过期时间)`，用来定位值在哪；再挂一层 LRU 读缓存兜住热点值，缓存满了淘汰最久未使用的。淘汰不会丢数据，读不到缓存就回磁盘拿。

启动恢复就是把所有段文件按编号升序重放一遍：SET 写进 KeyDir，DELETE 从 KeyDir 删掉，扫到坏记录（crc32 对不上、长度非法、文件被截断）就认为后面全是垃圾，停下并把该段截断到最后一条有效记录末尾。TTL 是惰性判断的，没起后台清理线程。数据涨起来后用 `POST /kv/compact` 收拾：遍历 KeyDir，把每个存活键只重写一条记录到临时目录，再整体替换掉旧段，读缓存跟着清空重建。

### 用户隔离一律用 WHERE user_id 兜底

这是我们吃过亏之后定下的规矩。courses / deadlines / notes 三张表都带 `user_id`，所有涉及用户数据的查询，SQL 里一律带上 `WHERE user_id = ?`，user_id 从 JWT 里解出来，请求体里根本没有这个字段。按 id 取单条时也是 `WHERE id = ? AND user_id = ?` 一起查，查不到统一返回 404，而不是先查出来再比对属主、不等返回 403——后者等于告诉对方「这个 id 存在，只是不属于你」，能拿来探测别人数据的存在性。所有涉及用户数据的接口都套着这条规则。

### 响应信封与错误码统一

后端 `/api` 下所有接口都套 `{ code, message, data }` 信封，`code` 为 0 才算成功。异常处理收在 `backend/app/core/errors.py` 一个文件里，按路径分流：走 `/api` 的校验错误包成信封、状态码 422，走 `/kv` 的压成 400 且只返回 `{"detail": "..."}`。之所以合并在一处，是因为 Starlette 的异常处理器按异常类存字典，同一类注册两次会被后者直接覆盖，之前 `/kv` 和 `/api` 各写一份就踩过这个坑。前端在 fetch 封装里统一拆信封，`code != 0` 当业务错误抛出来；401 单独处理，但排除登录 / 注册两个接口，否则一次正常的「用户名或密码错误」会把用户从登录页弹走。

### 课程周视图

课程页不是普通列表，是用 CSS Grid 手搭的一张周视图：行是 08:00 到 22:00 每 30 分钟一格，共 28 格，列是时间轴加周一到周日。每门课按 `day_of_week` 定横坐标、按起止时间换算成跨行数，画成一张卡片盖在格子上。时间落不到这个区间里的课（比如早八之前的），单独列在下面，不硬塞进网格。

### KV 的 compaction 与 benchmark

KV 这块另外留了两个能独立跑的东西。一个是 `POST /kv/compact`，把同一个键的多条历史记录合并成每个存活键一条最新记录。另一个是 `backend/scripts/bench_kv.py`：用同一份 2000 个键的数据集，把 Python dict、sqlite3、以及 KVEngine（热缓存 / 近似冷读两档）的读写单次耗时拉成一张对齐的表打印出来。这脚本只用来横向感受量级，不设阈值也不做断言，退出码固定为 0。

### 后端测试

后端 pytest 一共 117 个用例，全部通过。覆盖 auth、courses、deadlines、notes 的接口行为（含越权和参数校验）、模型的级联删除和唯一约束，以及 KV 引擎的编解码、LRU、引擎读写与恢复、`/kv` 路由。

## 已知限制

- KV 引擎只支持单进程：一把进程内的可重入锁把段文件 I/O 和 KeyDir 串行化，不支持多进程共享。
- KV 写入只在用户态把缓冲区刷给操作系统就返回，不做强制落盘，整机掉电时可能丢掉最后几条刚写的记录。
- JWT 黑名单还没实现：契约里写了「黑名单存 KV」，但项目没有 logout 接口，现在退出登录只是清掉本地 token，服务端的 token 在过期前依然有效。
- 笔记页不渲染 Markdown：正文按纯文本编辑、按纯文本显示，预览功能还没做。
- 课程周视图不做同格避让：同一时段同一天的课会叠在一起；`week_range`（如 "1-16"）只在表单里编辑、在卡片上展示，不参与渲染计算，因为项目里没有「当前第几周」这个概念。

## 后续可扩展

KV 引擎和业务库目前是两条独立的线，业务仍然走 SQLite，后续可以考虑把会话、热点缓存之类的场景接上 KV。算法可视化这边，排序和图遍历用的都还是前端内置的算法，没有做成可上传自定义算法。
